**Aura Context** is where AuraOS keeps environment variables and secrets —
things like `GITHUB_TOKEN`, `OPENAI_API_KEY`, or a plain `LOG_LEVEL`. You set
them once in **Settings → Context**. **An app gets a key only when it declares
it and you grant it**; nothing is handed to every app.

There are two places a value lives:

- the **System Context** (`context:system:*`): set in Settings → Context;
- each user's **vault** (`context:user:<userId>`, Settings → Users & Identities
  → Secrets): personal keys, which belong to that user. An app acting for that
  user reads one only with the user's own raw-read grant, and every read is
  audited.

---

## How a key reaches an app

1. The app **declares** the key in its manifest:
   ```json
   { "context": ["OPENAI_API_KEY"] }
   ```
2. The owner **grants** it: the install or update approval of an app that
   declares keys grants them (the dialog lists them), or directly:
   ```sh
   aura admin grant com.example.app context.read:OPENAI_API_KEY
   ```
   A personal key in a user's vault needs that user's `credential.read:<KEY>`
   grant instead (asked for with `osClient.credentials.request`).
3. At the app's next start, the key is in its env as `$OPENAI_API_KEY`, and
   `osClient.context.get('OPENAI_API_KEY')` returns it. For an instance that
   acts for a user, the user's vault is asked first, then the System Context.

A key the app does not declare is never in its env, and `context.get` refuses
it (403 `context-undeclared`). A declared key the owner has not granted is
refused too (403 `context-not-granted`). Revoking the grant takes effect for
`context.get` at once and for the env at the next start. A sidecar's
`envInherit` gets only keys its app holds.

There is no `/run/context` in apps any more.

## The two choices per entry

Every System Context entry has a **kind** and zero or more **inject** targets.

### Kind — how it's shown

| Kind | In the UI | Returned by the API |
|---|---|---|
| `secret` | masked (`••••`), never shown again | value withheld |
| `variable` | value visible and editable | value included |

### Inject — where it may appear

| Target | Delivered as | Update behaviour |
|---|---|---|
| `env` | `$KEY` in the apps that declare and hold it | app **respawn** to pick up a change |
| `file` | `/run/context/KEY` in the AuraOS shells only (the master) | **live** — no respawn |

No target at all keeps the key OS-only: no app gets it, even with a grant
(`context.get` of a granted OS-only key still works). A key must be a valid
env-var name: `[A-Z_][A-Z0-9_]*` (e.g. `GITHUB_TOKEN`, `LOG_LEVEL`).

## Where values show up

### In an app container

```sh
echo "$GITHUB_TOKEN"        # declared, granted and injected as env (set at spawn)
```

On the server, prefer `osClient.context.get('GITHUB_TOKEN')`: it reads the
current value without a restart.

### In the master (shell) container

The master is one long-running process, so a real `$ENV` var can't change in
it without a restart. Instead, **File**-injected values are exposed there:

```sh
cat /run/context/GITHUB_TOKEN       # live
aura jump -m                        # new master shell...
echo "$GITHUB_TOKEN"                # ...exports File entries automatically
```

Any newly-opened master shell auto-exports the File-injected values as
`$KEY`. Already-open shells pick them up on the next shell.

## Managing context

### Settings UI

**Settings → Context** lists every entry with its type and inject targets, and
lets you add or delete one. Secrets are masked; variables show their value.
Adding a key that already exists prompts for override.

### API

```sh
# list (secret values are withheld)
curl localhost:3000/api/os/context

# upsert
curl -X POST localhost:3000/api/os/context \
  -H 'Content-Type: application/json' \
  -d '{"key":"GITHUB_TOKEN","value":"ghp_...","kind":"secret","inject":["env","file"]}'

# delete
curl -X DELETE localhost:3000/api/os/context/GITHUB_TOKEN
```

`kind` defaults to `secret`, `inject` defaults to both targets. Setting a
value grants it to nobody: grant `context.read:<KEY>` per app.

## Storage & security

- Values are stored in the OS KV store under the isolated `context:system:*`
  namespace and **sealed with AES-256-GCM** at rest — nothing sits plaintext
  in the on-disk snapshot.
- The master key comes from `AURA_CONTEXT_KEY` (base64 of 32 bytes, e.g.
  `openssl rand -base64 32`). In dev, a key is generated automatically; set it
  explicitly in production.
- The public KV proxy (`/api/kv/...`) **refuses** the `context:*` namespace, so
  an app can't read another entry's raw value out of band. Context reaches an
  app only as its granted env and through `osClient.context.get`.
- The master's materialised `/run/context/<KEY>` files are plaintext by
  necessity; no app mounts them.

---

## Gotchas

- **Env changes need a respawn.** Container env is fixed at start. Change an
  `env` value or a grant → restart the app to see it in its env
  (`context.get` sees it at once).
- **Declared but not granted** means not there: check `aura admin grants`.
- **Already-running apps** spawned before an entry existed won't have it until
  their next spawn.
- **Master shells** must be freshly opened after a change to see updated
  `$KEY` values (files are always current).
- Keys are env-var names only (`[A-Z_][A-Z0-9_]*`).

## Not yet

- **App Context** (`context:app:<id>:*`) — per-app entries. The schema is
  reserved; the System Context with per-app grants and the users' vaults ship today.
