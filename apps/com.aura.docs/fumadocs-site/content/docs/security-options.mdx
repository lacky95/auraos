---
title: Security options
description: Every security switch of AuraOS in one list — its default, where its value comes from, and how to change it.
---

AuraOS declares every security switch once, in the **security options
registry** (core `security/options.ts`). Settings, the CLI, the API and the
diagnostics all read that one list. A test keeps this page in step with it.

```bash
aura admin security            # every option: value, source, how to set it
aura admin security set <id> <value>
```

`GET /api/admin/security-options` returns the same list (an owner view).

## Where a value comes from

- **policy**: stored by AuraOS in one sealed record (`user:policy:security`)
  that only the owner changes. A change needs your password in AuraOS's own
  dialog (`fresh`), from Settings or the System Terminal; on the host,
  `docker exec -it aura-shell aura admin security set …` acts directly. A
  record that fails its integrity check counts as the defaults, and the audit
  trail says so.
- **env**: set on the host, in `docker-compose.yml` or `.env`, then
  `aura restart os`. Shown here, never set here: the API answers 409 with the
  variable to set.
- **record**: has its own sealed record and its own place to change it.
- **file**: has its own switch file under `/data/aura/` and its own command;
  a host variable wins over the file. Shown here, changed where it always was.
- **reserved**: declared for later; not yet available.

A host variable always wins over the stored value.

## The options

| Id | Default | Source | What it does |
|---|---|---|---|
| `fresh-auth-require-https` | off | policy | **Require HTTPS for password confirmations.** Off: an approval that needs your password ("fresh") works in the desktop dialog over plain HTTP too, with the note "(HTTP: password sent unencrypted)". On: over HTTP it needs `aura approve <id>` on the host; over HTTPS the dialog still takes the password. Turn it on if AuraOS is reachable from networks you don't trust. While it is on, turning it off over HTTP needs HTTPS or the host. Settings → Users & Identities → Global. |
| `password-policy` | 4 characters, 0 types, differs from username | record (`user:policy:password`) | The rules for new and changed passwords. Settings → Users & Identities → Global. |
| `access-enforce` | report | env `AURA_ACCESS_ENFORCE` | `off`: no access report. `report`: decisions are counted in `aura admin access-report`, nothing refused. `enforce`: what the route access manifest denies is refused. App Host gateway calls are enforced in every mode. |
| `lifecycle-strict` | warn | env `AURA_LIFECYCLE_STRICT` | `warn`: an app whose lifecycle checks fail still starts, with a finding. `strict`: its start is refused. |
| `relay-strict` | strict | env `AURA_RELAY_STRICT` | The Terminal and aurashelld act for a user, so they answer only calls the shell relays. The shell signs each relayed call with a relay claim (`x-aura-relay`, keyed per app start, bound to the instance, method and path; D89 B4); the kernel's own lifecycle calls carry the lifecycle token instead. `strict` (the default since 5-main): a call from the shell's address without a valid claim is refused; the address alone proves nothing. `warn`: it is still served and logged in that app's log (`[shell-peer] relay-claim missing\|invalid`); a rollback aid only. Applies to app starts after the change. |
| `terminal-root-transition` | off | file `/data/aura/terminal-root-transition` | The 5-main deploy's one migration window (stream T). `deploy` in a root-owned file written less than 6 hours ago lets the owner's System Terminal start as root while the owner's Private Home still belongs to root (before `aura admin homes ownership --apply`). Never a member's Terminal. `off`, a missing file or an expired one: a Terminal whose user's home is not theirs does not start (no root fallback). No host variable. |
| `host-policy` | enforce | env `AURA_HOST_POLICY` | `enforce`: a malformed address, or a custom domain not listed, is refused (DNS rebinding protection). `report`: served and logged. |
| `desktop-hosts` | (none) | env `AURA_DESKTOP_HOSTS` | Custom domains AuraOS is opened at; their App Hosts follow. IPs, localhost and nip.io need no entry. See [Reaching AuraOS](/docs/reaching-auraos). |
| `trusted-proxies` | (none) | env `AURA_TRUSTED_PROXIES` | Addresses whose `X-Forwarded-Proto`, `-Host` and `-For` count: your HTTPS edge. Empty: a request is HTTPS only when it really is. |
| `system-mode` | developer | file `/data/aura/system-mode`, env `AURA_SYSTEM_MODE` | `developer` (the default until Phase 6): AuraOS runs from its `/workspace` checkout, `aura mount workspace`, `aura dev rebuild` and `aura dev restart` work, and the desktop shows the "Developer mode" badge. `normal`: those are refused; the locked release comes with Phase 6. Turning it on needs your password; turning it off lists what differs from the release first. Settings → System, or `aura mode`. See [Developer Mode](/docs/developer-mode). |
| `shell-mode` | dev | file `/data/aura/shell-mode`, env `AURA_SHELL_MODE` | `dev`: the shell runs `astro dev` from source (HMR). `prod`: its production build, no dev server. Takes effect on the next `aura restart os`. `aura shell mode`; one approval click (owner decision Phase 4, D57). |
| `runtimes` | container and PRoot enabled | record (`user:policy:runtimes`) | Which runtimes apps may run in, the default for apps that name none, each runtime's settings and per-installation overrides. A change applies to an app's next start; an unknown or disabled runtime is refused, never replaced. Settings → Runtimes, or `aura runtime` (Phase 5, the runtime release). |
| `app-run-as` | per installation | record (`apphost:install:<installationId>`, field `runAs`) | How an installed app's processes run. `app`: as the installation's own app identity (uid 200000+), with no capabilities and `no-new-privileges`; its data belongs to that identity, its source stays root-owned. `root`: as before. Installations from before 5-apps run as root; new installations start as `app` (built-in apps stay root until you flip them). A failed `app` start is never retried as root. A flip that changes the uid moves the app's managed storage (its instance data, App Homes and dev caches; never a Private Home, a mount or another app's data) through the reviewed ownership migration: `aura admin apps run-as <app> app\|root` is a dry run with a digest, `--apply <digest>` (your password) stops the app and the instances that mount its data, applies it journaled, flips and starts them again only after it succeeded. Only entries the previous identity owns change; the flip back restores the earlier migration's journal exactly, then hands what the app created since to root. A failed apply is restored and the app stays stopped; an interrupted one keeps the app from starting until `aura admin apps run-as <app> --recover` restores its journal. No capability is added. `aura admin apps privileges` is the review (Phase 5). |
| `app-root-execution` | approve | policy | An app may *request* root in its manifest (`execution: { runAs: "root", reason }`); a request is never a grant. `approve`: you approve it with your password in the install or update dialog (shown under **High risk**), or later with `aura admin apps run-as <app> root`. The approval is bound to the installation and that exact config (digest, audited `app.execution-approved`); an update that introduces or expands it asks again. Approved root is runtime root only: no capability, `no-new-privileges`, no Docker socket, no host access; the PRoot runtime refuses it. `refuse`: no root request runs. Either way an app whose request is not approved is installed but does not start ("root execution not approved"). Legacy root installations from before 5-apps are a migration state, listed as such by `aura admin apps privileges`. Phase 5. |
| `proot-host` | off | env `AURA_USE_PROOT` (docker-compose sets `true`) | Whether the PRoot runtime can run apps at all. On (`true`): PRoot apps run wrapped in PRoot under their own app identity, with a narrowed view: only the shared workspace packages (no other app's source), no `/run/context`, no Docker socket, their App Home and their own `/tmp`. Off (unset or `false`): the PRoot runtime is unavailable and a PRoot app's start fails closed; PRoot never runs an app unwrapped in the AuraOS container (Phase 5). |
| `aura-root` | enabled | policy | `enabled`: the owner can open a dedicated root tab (`aura root` in their own Terminal) with the Docker socket in that tab's session only, after a password approval, audited (`root.granted`, `root.ended`). `disabled`: `aura root` is refused. A tab already open stays until it ends (`aura root end`). Phase 5. |
| `access-profile` | open | reserved | Open, or Zero Trust (every app call needs an explicit grant). Not yet available. |

A full **Security** page in Settings comes later; until then the HTTPS switch
lives under Users & Identities → Global.
