---
title: Bring-your-own-runtime apps
description: Wrap a foreign Docker image (an agent, a model server, a dashboard) as an AuraOS app whose window is that image's own UI.
---

Some apps aren't a web server of their own. They wrap a whole external
runtime: an agent, a model server, a registry, a database with an admin UI.
AuraOS runs every app container from the shared `aura-base` image, so an app
**can't be** a foreign image directly. Instead it is a thin **controller**:
the foreign image runs as a [sidecar](/docs/sidecars) next to it on
`aura-net`, and the controller reverse-proxies the sidecar's UI into the app
window.

The SDK does all of it: `createSidecars(...).listen()` starts the sidecar,
answers the lifecycle contract on `$APP_PORT`, and proxies the dashboard,
in about a dozen lines. Let the **OS** start the sidecar (`mode: 'os'`):
the controller then needs only the `sidecars.spawn` permission, no docker
tool and no host root.

This page covers what is specific to wrapping a runtime: the controller, the
proxy, auth and rendering. Everything about the sidecar itself (template
fields, volumes, seeding, inheritance, exec, logs, lifecycle) is in
[Sidecars](/docs/sidecars).

## 1. Declare the runtime in the manifest

The app is a `raw` runtime in a container sandbox; the foreign image is a
`services[]` template marked `proxyDashboard`.

```jsonc
{
  "id": "com.example.agent",
  "componentType": "activity",
  "runtime": "raw",
  "sandbox": "container",
  "tools": ["bash", "node"],
  "permissions": ["sidecars.spawn"],
  "serverPort": 4110,
  "proxy": { "rewriteHtml": "astro" },
  "services": [
    {
      "name": "runtime",                       // container aura-<instanceId>--runtime
      "image": "vendor/their-image:tag",
      "command": ["serve", "--port", "8080"],  // many images exit without a subcommand
      "port": 8080,                            // what the proxy forwards to
      "proxyDashboard": true,                  // this service's UI is the app window
      "env": { "SOME_FLAG": "1" },
      "volumes": [{ "name": "data", "target": "/var/lib/app" }],
      "dns": ["8.8.8.8", "1.1.1.1"]            // sidecars get no DNS by default
    }
  ]
}
```

`proxyDashboard` may be set on one service. Volumes land in the app's data
dir and survive restarts and updates. All other fields:
[Templates](/docs/sidecars/templates).

## 2. Wire it up

```js
// server.mjs (runtime: "raw", the entrypoint runs `node server.mjs`)
import { readFileSync } from 'node:fs';
import { fileURLToPath } from 'node:url';
import { createSidecars } from '@aura/app-sdk/sidecars';

const HERE = fileURLToPath(new URL('.', import.meta.url));
const manifest = JSON.parse(readFileSync(HERE + 'app.manifest.json', 'utf8'));

createSidecars({
  appId:      process.env.APP_ID,
  instanceId: process.env.APP_INSTANCE_ID,
  appPort:    Number(process.env.APP_PORT),
  services:   manifest.services,
  mode:       'os',
}).listen();
```

That is a complete bring-your-own-runtime app. `listen()` serves on
`$APP_PORT`:

- the lifecycle contract. Health answers **immediately**, so a slow first
  image pull can't blow the OS's 60 s health window; `onStart` asks the OS
  for the sidecars (idempotent), `onDestroy` removes them;
- a streaming reverse proxy (HTTP and WebSocket) to the `proxyDashboard`
  service, with a "starting…" page until it answers;
- `/api/status` with the current phase.

`@aura/app-sdk` resolves from the workspace `node_modules` mounted into every
container; no `aura install sdk` needed.

Need first-run config in the runtime's volume? Use `services[].seed`
([Seeding](/docs/sidecars/templates#seeding)). An existing app on the
default `mode: 'docker'` path:
[migrate it](/docs/sidecars/app-managed#migrate-to-os-managed).

### Auth injection (optional)

If the runtime's UI is behind a login, pass an `auth` hook so the user isn't
prompted twice. The SDK adds the returned headers to every proxied request
(HTTP and WS) and re-authenticates on an auth bounce:

```js
createSidecars({
  /* …ctx, services, mode… */
  auth: {
    async headers() { if (!session) await login(); return { cookie: session }; },
    isAuthBounce: (status, loc) => status >= 300 && status < 400 && /\/login/.test(loc),
    async reauth() { session = ''; await login(); },
  },
});
```

## 3. Rendering fidelity

A third-party dashboard ships its own complete styling, and you usually want
it to look exactly like it does natively. Two manifest settings control what
the shell proxy injects into the app document:

- **`themeStrategy: "override"`** (top-level) stops the proxy injecting
  `<link rel="stylesheet" href="/api/os/theme.css">`. That stylesheet is
  mostly harmless `:root { --aura-* }` variables, but it also carries global
  `*` and `::-webkit-scrollbar` rules that restyle the app's scrollbars.
  (The Process Manager shows an `OVERRIDE` chip so users know why it looks
  different.)
- **`proxy.injectMeta: false`** drops the non-rendering `aura-*` meta tags
  (design framework, theme, keymap). Optional; the identity meta
  `aura-app-id` / `aura-instance-id` always stay, so the iframe identity
  gate is unaffected.

Keep `rewriteHtml: "astro"` even so: it rewrites the runtime's root-absolute
`/assets/*` tags to `/api/proxy/<id>/assets/*` and doesn't touch appearance.
SPAs that emit root-absolute URLs from script may need
`rewriteHtml: "absolute"` plus `preservePrefix`. `com.aura.hermes` uses
`themeStrategy: "override"` + `injectMeta: false` to render the Hermes
dashboard natively.

## Requirements & caveats

- `sandbox: "container"` and `sidecars.spawn`. The docker path instead needs
  `tools: ["docker"]`, which is host root; see
  [App-managed sidecars](/docs/sidecars/app-managed) for when that is still
  the right call.
- Don't publish host ports. On the OS path `publish` needs
  `sidecars.privileged`.
- The host docker daemon must be able to pull the image. A failed pull
  fails the spawn; the app itself still boots and its window shows the
  error.
