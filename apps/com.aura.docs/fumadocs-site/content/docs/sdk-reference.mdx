A flat, scannable reference for `@aura/app-sdk`. Mirrors the source —
`packages/app-sdk/src/`. Each entry: signature, one-line purpose, a
short example. Tags after the signature: **(B)** browser-only, **(S)**
server-only, **(B+S)** both.

For the conceptual model, read [Core Concepts](/docs/core-concepts).
For the lifecycle factories in context, read [Develop an App](/docs/develop-an-app).

## OsClient — top-level

Instantiate once, in the browser (or server-side for the few async
methods that take an URL):

```ts
import { OsClient } from '@aura/app-sdk';
const os = new OsClient();
```

### Content providers

Authority is the declaring app's id; resource is the path *after*
`/api/data/<authority>/`. Permissions enforced by `PermissionManager`.

| Method | Signature | Note |
|---|---|---|
| `queryProvider<T>` | `(authority: string, resource: string) => Promise<T>` | **(B+S)** GET. |
| `writeProvider<T>` | `(authority: string, resource: string, body: unknown, method?: 'PUT' \| 'POST' \| 'PATCH' \| 'DELETE') => Promise<T>` | **(B+S)** Method defaults to PUT. |
| `watchProvider` | `(authority: string, resource: string) => EventSource` | **(B)** SSE. Provider must serve `?watch=1`. |

```ts
const notes = await os.queryProvider('com.example.notes', 'list');
await os.writeProvider('com.example.notes', 'list', { title: 'Hi' });
const es   = os.watchProvider('com.example.notes', 'list');
es.onmessage = (e) => console.log(JSON.parse(e.data));
```

## osClient.notifications

Create, change and remove your own notifications, read them, wait for a
dialogue answer, and follow their lifecycle live. Source:
`packages/app-sdk/src/notifications.ts`. REST:
`/api/notifications`. The full guide (types, components, permissions, lock
screen, retention, MCP) is [Notifications](/docs/notifications).

**Who you are.** On the server (Node: lifecycle endpoints, Astro
frontmatter, backends) every call sends
`Authorization: Bearer $AURA_INSTANCE_TOKEN`, so the shell attributes the
notification to your app as **verified**. In the browser no token is ever
sent, so the caller is **unverified**. The browser client remembers the
`senderToken` it got from `create`, so the same page can still update or
remove its own notifications.

**Permissions** (in `app.manifest.json` `permissions[]`):

- `system.notifications` lets an app send. A verified app without it gets
  **403**.
- `notifications.locked` (Locked: the user can't dismiss it) and
  `notifications.popup` (a dialogue opens as a pop-up) are privileged. The
  manifest only **requests** them; an admin grants them with
  `aura grant nperm <app> locked|popup` or in Settings → Notifications &
  access.
  - Without the grant the request is **downgraded**: locked becomes simple,
    and the pop-up is turned off. A `warnings[]` entry says why.
  - Grants and revokes take effect at once, without a restart.
  - Even with the grant, a sender gets at most **3 forced pop-ups per 10
    minutes**. After that `popup` is turned off with a warning, and the
    dialogue waits in the list.

**Dialogue placement** (`type: 'dialogue'`):

- `context` decides where the dialogue opens. With
  `{ kind: 'activity' | 'instance', id }` of your own window, it opens over
  that window. The window stays usable: the dialogue is a collapsible panel
  at the bottom.
- `blocking: true` makes **only your own window** inert until the user
  answers. Its title bar and the rest of the desktop stay usable. The shell
  checks that the activity or instance belongs to the calling app; it never
  trusts `context.appId`. Agents, API keys, browser (unverified) callers and
  contexts of another app get `blocking: false` and a warning.
- A dialogue never fetches a minimized window or one on another workspace.
  It waits in the list with **Answer**, and the window's chip or workspace
  pill gets a marker. Pressing Answer reveals the window.
- Without a window (a background app or an agent) the dialogue floats over
  the desktop when the user presses Answer, or at once with an allowed
  pop-up. It never blocks the desktop.
- `scope: 'desktop'` is a desktop-wide modal reserved for AuraOS system
  decisions. Everyone else is downgraded to `scope: 'auto'` with a warning.

**Locked** (`type: 'locked'`): the user can't dismiss it, and Clear all
skips it. The user can still force-remove it from the card's ⋯ menu after a
confirmation. The sender then sees `state: 'removed'` with
`removedReason: 'force-removed'` in `get`, `subscribe` and
`waitForAnswer` (`r.removedReason`).

**Rules for verified apps:**

- An app changes only its own notifications.
- An app reads its own notifications in `get`, `list` and `subscribe`,
  including their answers and interaction results.
- An app can create at most 30 notifications per minute. Beyond that it
  gets 429.

**Reading other senders' notifications** needs the privileged
`notifications.read`: the manifest requests it, and an admin grants it
with an explicit scope:

```sh
aura grant nperm com.example.dash read --scope app:com.example.notes
aura grant nperm com.example.dash read --scope sender:auraos,app:com.example.ci --include-secret
aura grant nperm com.example.dash read --scope all
aura revoke nperm com.example.dash read
```

- The scope lists apps (their verified items), sender keys (`app:<id>`,
  `auraos`, `key:<keyId>`, `anon:rest`, …) or `all`. Secret items are left
  out unless the grant has `--include-secret`. The same grant works for API
  keys (Settings → Notifications & access, or `POST /api/admin/grants` with
  `readScope`).
- Read access is the same in `get`, `list`, `waitForAnswer` and
  `subscribe`. A read grant does not let an app change, dismiss or answer
  someone else's notification (403).
- Lock-screen visibility is not read access: `public` never makes an item
  readable for other apps.
- The browser (unverified) reads nothing, except its own items by id:
  `get` and `waitForAnswer` send the `senderToken` remembered from
  `create`. A caller with neither credentials nor a shell client session
  gets an empty list, 404 and an empty stream.

**Pop-up duration** (`popupDurationMs`, optional) is how long the shell
shows the pop-up. It is separate from `timeoutMs`, which is how long the
notification lives.

- Absent: the default. Low and medium pop-ups hide after 8 s, high and
  urgent ones stay until handled.
- `> 0`: the pop-up hides after that many ms; the item stays in the list.
- `0` or `-1` (any negative is stored as `-1`): a sticky pop-up. It stays
  until the user dismisses, opens or answers it, or the item is removed or
  expires. A sticky pop-up holds one of the 3 pop-up slots and is never
  pushed out; with three sticky ones, new items go to the list only.
- An integer up to 24 h. In `update`, `null` goes back to the default.
- Hovering or focusing a timed pop-up pauses it.

**Lock screen** (`visibility`, default `private`): while AuraOS is locked,

- `public` shows the title and text, but no buttons, inputs or answer;
- `private` shows only the sender and `publicTitle` / `publicText` (or
  "New notification");
- `secret` is not shown at all.

The user can make a sender stricter (never less strict), hide everything on
the lock screen, and set how long ended notifications are kept (Settings →
Notifications & access → Lock screen & history). The shell enforces this on
the server for each browser tab (a *client session*, see the privacy note
below), not only in the UI.

**Retention.** Ended notifications (resolved, dismissed, cleared, expired,
removed) are kept as history for 7 days by default (1, 7, 30 or 90 days,
or forever, also per sender), then deleted together with their history.
Active notifications are never deleted automatically; only their
`timeoutMs` ends them. `DELETE /api/notifications/history[?sender=]`
("Clear history now" in the list's ⋯ menu) deletes ended items at once.

| Method | Signature | Note |
|---|---|---|
| `create` | `(input: NotificationInput) => Promise<{ notification, senderToken?, warnings }>` | **(B+S)** `type: 'simple' \| 'locked' \| 'dialogue'`, `title`, `text`, `priority`, `visibility`, `publicTitle`, `publicText`, `timeoutMs`, `popupDurationMs`, `pinned`, `popup`, `blocking`, `scope: 'auto' \| 'desktop'`, `components[]` (input, options, select, combobox, button, progress), `context {kind, id, label?}`. `priority` is `low`, `medium`, `high` or `urgent`. |
| `update` | `(id, patch, { senderToken? }?) => Promise<{ notification, warnings }>` | **(B+S)** Your own only. `null` clears a field. `type` is fixed. |
| `remove` | `(id, { senderToken? }?) => Promise<Notification>` | **(B+S)** You are done with it (reason `completed`). Dismissing is the user's action. |
| `get` | `(id) => Promise<Notification \| null>` | **(B+S)** `null` when not found, or not readable for you (not yours and not covered by a read grant). |
| `list` | `(filter?: { state?, sender?, priority?, limit?, cursor? }) => Promise<{ items, nextCursor? }>` | **(B+S)** `state` defaults to `active`. |
| `waitForAnswer` | `(id, { timeoutMs?, signal? }?) => Promise<{ status: 'resolved' \| 'removed' \| 'pending', notification, answer?, outcome?, removedReason? }>` | **(B+S)** Bounded long-poll (≤ 25 s per request) until the notification is answered or removed. `pending` after `timeoutMs` (default 60 s). `outcome` is `submitted` or `cancelled` once resolved. `removedReason` says why it was removed, e.g. `force-removed`. |
| `waitForInteraction` | `(id, { after?, timeoutMs?, signal? }?) => Promise<{ status: 'interaction' \| 'resolved' \| 'removed' \| 'pending', notification, interaction?, outcome?, answer?, removedReason? }>` | **(B+S)** Like `waitForAnswer`, but also returns on the next user interaction (a button without `action`, an input submit, an options / select / combobox choice): `interaction = { componentId, kind, value?, values?, at }`. `after` (ms): only newer interactions count; default the current `lastInteraction.at`. Pass the last `interaction.at` back so none is missed. Long-poll `?waitFor=interaction&after=`. |
| `subscribe` | `(handler: (ev) => void, { since?, onError? }?) => () => void` | **(B+S)** Live feed (SSE `/api/notifications/stream`). Browser: `EventSource`. Node: a stream parser that sends the Bearer. Both resume with `Last-Event-ID` after a drop. |
| `simple` | `(title, text?) => Promise<CreateResult>` | **(B+S)** Same as `sendNotification`. |

Each `subscribe` event has the shape
`{ type: 'notification:<event>', eventId, event, id, state, notification }`.
`notification` is the item's current full state, including `answer` once it
is resolved. A `{ type: 'reset' }` event means: reload with `list()`. Treat
unknown `type`s as forward-compatible; ignore them, or refetch the item.

**Standard dialogue buttons** (`role`). Every dialogue gets three special
buttons. The shell adds any you leave out, in the order: your custom
buttons, then Later, Cancel, Submit (the primary one on the right; stacked on
a phone).

| `role` | Default text | What it does |
|---|---|---|
| `submit` | "Submit" (with inputs or options), else "OK" | Always primary. Checks required fields, then resolves with `answer: { outcome: 'submitted', buttonId, values }`. |
| `cancel` | "Cancel" | No validation, no values. Resolves with `answer: { outcome: 'cancelled', buttonId }`, so you learn the user said no. |
| `later` | "Later" | Local only: hides the dialogue; nothing is sent, and it stays in the list with Answer. Not on blocking dialogues or desktop decisions. The dialogue header's ✕ does the same. |

- A role button may give only its text, e.g. `{ kind: 'button', role: 'cancel', label: 'No thanks' }`.
  `id` defaults to the role, and `label` to the default text. There can be
  at most one button per role. Custom buttons (no `role`) need `id` and `label`.
- A resolved item has a top-level `outcome: 'submitted' | 'cancelled'` next to
  `answer`. A resolve without one counts as `submitted`.
  `waitForAnswer` returns it as `r.outcome`.
- What the user types is kept as a draft in the browser (localStorage) until
  the dialogue is answered or removed, so a reload doesn't lose it.

How the shell answers other buttons:

- A button with `action: 'resolve'` acts like a submit: it resolves the notification with the answer
  `{ outcome: 'submitted', buttonId, values }`. `values` holds the current input and options
  values by component id: a string, or an array of option ids when
  `multiple` is set.
- **options** take `display: 'segmented' | 'radio' | 'checkbox'`:
  segmented chips (single choice, the default, ≤ 4 options), a radio list
  (single choice, ≤ 8) or a checkbox list (`multiple: true` — its default
  and only display, ≤ 8). Each option may have a `description` (≤ 200),
  shown under its label in the lists (the tooltip on a chip). A mismatch
  (`radio` / `segmented` with `multiple`, `checkbox` without) → 400.
- **select** (`options` 1–50, `default?`) is a dropdown; its value is an
  option id. **combobox** (`options` 0–50, `allowCustom?`, `default?`) is
  searchable; its value is an option id or, with `allowCustom`, the typed
  text (≤ 200). The server checks these values in interactions and in
  `answer.values` (400 for an unknown option).
- A button **without** `action`, an input submit (Enter) and an options,
  select or combobox choice keep the notification active. Each one sends a
  `notification:interacted` event, and the item's `lastInteraction` is
  `{ componentId, kind, value?, values?, at, actor }`.
- `action: 'dismiss'` dismisses the notification, and `action: 'link'`
  opens `href` (http(s) only).

```ts
const { notification, warnings } = await os.notifications.create({
  type: 'dialogue',
  title: 'Deploy release 1.4 to production?',
  components: [
    { kind: 'button', role: 'submit', label: 'Deploy' },
    { kind: 'button', role: 'cancel', label: 'Not now' },   // Later is added by the shell
  ],
  context: { kind: 'task', id: 'deploy-42', label: 'Release 1.4' },
});
if (warnings.length) console.warn(warnings);          // e.g. a pop-up without the grant

// Keep working; check back for the answer.
const r = await os.notifications.waitForAnswer(notification.id, { timeoutMs: 120_000 });
if (r.status === 'resolved') console.log(r.outcome, r.answer);   // 'submitted' | 'cancelled'

// Progress on a running job, then done:
await os.notifications.update(notification.id, { components: [{ kind: 'progress', value: 0.5 }] });
await os.notifications.remove(notification.id);

// Live:
const stop = os.notifications.subscribe((ev) => {
  if (ev.type === 'notification:resolved') console.log(ev.notification?.answer);
  if (ev.type === 'notification:interacted') console.log(ev.notification?.lastInteraction);
});
```

API keys (`Authorization: Bearer aura_k1_…`, created by an admin with
`aura apikey create`) let external REST callers send verified
notifications too. They don't use the SDK.

### Privacy note: lock screen and client sessions

- **The lock screen has no PIN.** A click or a key unlocks it. Redaction on
  the lock screen protects against glances at an unattended screen, not
  against someone who sits down at it.
- Each shell browser tab registers a **client session**
  (`POST /api/os/clients`) and reports when it locks and unlocks. The
  notification API redacts for that tab on the server: list, get, the
  long-poll, the SSE stream (including its catch-up), the replies of user
  actions and the counts. A missing, unknown or expired session counts as
  locked. Another tab keeps its own state.
- A client session is **not a credential**. It grants no permission; it
  only picks the lock-screen view. A client-reported unlock is not an
  authentication boundary. The server has an `UnlockVerifier` hook where an
  authenticated unlock (PIN or user login) will plug in later.
- On lock the shell clears the notification list, pop-ups and open
  dialogues at once, and reloads only after the server confirmed the lock.
  After a reconnect it re-syncs the lock state before it loads anything.
- Known gap: app frontends share the shell's origin, so an app's browser
  code could register a client session of its own and read what an
  unlocked screen sees. This is closed only with per-app origins and user
  accounts.

## osClient.keymap

Declare actions in `manifest.keymapActions`; register handlers here.
The SDK namespaces actions to `app.<appId>.<id>` automatically.

| Method | Signature | Note |
|---|---|---|
| `on` | `(actionId: string, handler: (ctx: {actionId, combo}) => void) => () => void` | **(B)** One handler per action. |
| `off` | `(actionId: string) => void` | **(B)** |
| `getBinding` | `(actionId: string) => string \| null` | **(B)** Synchronous; reads meta tag. |
| `onChange` | `(cb: (info: {actionId, oldCombo, newCombo}) => void) => () => void` | **(B)** Fires on remap. |

```ts
os.keymap.on('save', () => saveDocument());
const combo = os.keymap.getBinding('save');         // "Ctrl+KeyS" — for menu label
const stop  = os.keymap.onChange(({ actionId, newCombo }) => {
  if (actionId === 'app.com.example.notes.save') menuLabel.textContent = newCombo ?? '';
});
```

## osClient.nav

### Back-key

| Method | Signature | Note |
|---|---|---|


### `installGridNav`

Wires the user's basic-nav keys (`aura.nav.up/down/left/right`) to a
list/grid of focusable elements in your page. Reads the user's current
combo via `osClient.keymap.getBinding('aura.nav.up' …)` so remaps in
Settings → Keyboard take effect on next load. Also auto-focuses the
first element when the shell posts `aura.window.focus` (e.g. when the
user enters this window from window-selection mode or launches it).

```ts
interface InstallGridNavOptions {
  selector?:    string;                          // CSS selector
  getElements?: () => HTMLElement[];             // OR dynamic resolver
  pauseWhen?:   () => boolean;                   // skip when true (e.g. modal open)
  onFocus?:     (el: HTMLElement) => void;
}
interface GridNavHandle {
  focusFirst(): void;   // force-focus the first element
  uninstall(): void;
}

os.nav.installGridNav({ selector: '.tile[data-section]' });
```

The helper bails inside `<input>`/`<textarea>`/`<select>`/
`[contenteditable]`, so typing always wins. Backspace and modifier
combos are never consumed.

## osClient.activity

In-place navigation within the current activity. The OS records a back
stack the user pops with the OS Back key (or `osClient.nav.onBack`'s
default fall-through).

| Method | Signature | Note |
|---|---|---|
| `navigate` | `(path: string, opts?: { title?: string; pushHistory?: boolean }) => Promise<boolean>` | **(B+S)** Pushes previous path on the stack by default. |
| `replace` | `(path: string, opts?: { title?: string }) => Promise<boolean>` | **(B+S)** Like `navigate` with `pushHistory: false`. |
| `back` | `() => Promise<void>` | **(B+S)** Pop one step. |
| `backTo` | `(index: number) => Promise<void>` | **(B+S)** Jump to position 0..n-1 in the stack. |
| `setBreadcrumb` | `(mode: 'os' \| 'off') => Promise<void>` | **(B+S)** Hide OS breadcrumb when app draws its own. |
| `getHistory` | `() => Array<{ path; title? }>` | **(B)** Reads meta tag; refreshed on every iframe load. |
| `getActivityId` | `() => string \| null` | **(B+S)** From `APP_ACTIVITY_ID` env or proxy meta. |

```ts
// Settings drills down: index → /theme → /keyboard, OS Back pops back.
await os.activity.navigate('/theme', { title: 'Settings · Theme' });
await os.activity.navigate('/keyboard');
await os.activity.back();   // → /theme
```

```js
import { auraAppIntegration } from '@aura/app-sdk/integration';
export default defineConfig({
  integrations: [auraAppIntegration()],
});
```

### Proxy helpers (`packages/app-sdk/src/proxy.ts`)

For apps that proxy upstream HTTP themselves (e.g. a content provider
that forwards to a backend service). **(S)** server-only.

| Symbol | Signature | Note |
|---|---|---|
| `proxyFetch` | `(upstreamUrl: string \| URL, req: Request, opts?: ProxyFetchOptions) => Promise<Response>` | Strips hop-by-hop + post-decompression headers; returns a sanitised Response. |
| `proxyFetch.raw` | `(…) => Promise<{ upstream: Response; headers: Headers }>` | Escape hatch when you need to inspect/rewrite headers before returning. |
| `sanitizeHeaders` | `(input: Headers) => Headers` | The standalone sanitiser. |

```ts
// src/pages/api/upstream/[...path].ts
import { proxyFetch } from '@aura/app-sdk/proxy';
import type { APIRoute } from 'astro';
export const ALL: APIRoute = ({ request, params }) =>
  proxyFetch(`http://localhost:8080/${params['path']}`, request);
```

### OS-managed sidecars (`packages/app-sdk/src/os-sidecars.ts`)

**(S)** server-only. Import from `@aura/app-sdk/os-sidecars` (also re-exported
by `@aura/app-sdk/sidecars`). The OS runs the containers from the app's
`services[]` templates; the app needs the `sidecars.spawn` permission, not the
docker tool. Guide: [OS-managed sidecars](/docs/sidecars/os-managed); routes,
request fields and return types: [HTTP API & SDK](/docs/sidecars/api).

| Symbol | Purpose |
|---|---|
| `osSidecars(opts?)` | Client for the calling instance. `opts`: `base` (default `OS_API_BASE` → `AURA_OS_URL`), `instanceId` (`APP_INSTANCE_ID` → `AURA_INSTANCE_ID`), `token` (`AURA_INSTANCE_TOKEN`), `timeoutMs` (15 min: a spawn may pull an image). |
| `.spawn(req)` | `{ template, name?/suffix?, env?, envInherit?, command?, mounts?, tools?, image?, replace?, takeover?, wait? }` → `{ created, sidecar, tools? }`. Same spec again → adopted (`created: false`); changed spec → recreated. `tools` = initial grants (needs `sidecars.tools`, a template with `tools`; merged on adopt, not part of the spec). |
| `.list()` / `.get(name)` / `.remove(name)` | The instance's OS sidecars; `get` → `null` if there is no such sidecar (a missing instance throws); `remove` also removes the sidecars it spawned. |
| `.exec(name, cmd[], { stdin?, timeoutMs?, user?, workdir?, env? })` | → `{ exitCode, stdout, stderr, truncated, timedOut }`. argv, no shell; default timeout 30 s, max 10 min. |
| `.logs(name, { tail?, since?, timestamps? })` | → `{ stdout, stderr }`. |
| `.mounts(name).list()` / `.add(appId, { mode?, data? })` / `.remove(mountId)` | The sidecar's cross-app mounts (own + inherited). Changing them needs `sidecars.mounts` + `apps.mount` and a sidecar spawned with `mounts: { own: true }`. |
| `.tools(name).list()` / `.grant(...tools)` / `.revoke(...tools)` | The sidecar's own tools at `/aura/my-tools`: `{ own, inherited, template, runtime, effective, ignored }`. Its template must declare `tools`, which needs `sidecars.tools`; always capped at the app's `tools[]`. See [Tools of a sidecar](/docs/sidecars/tools). |
| `OsSidecarError` | Thrown on failure; `.status` is the HTTP status (0 = no response); `.permission` names a missing permission on a 403. |

Inside an OS sidecar spawned with `inheritIdentity`, `osSidecars()` works
unchanged, with that sidecar's own token, so what it spawns becomes its child.

### Sidecars — bring-your-own-runtime (`packages/app-sdk/src/sidecars.ts`)

`createSidecars({ appId, instanceId, appPort, services, mode?, auth?, onSeed? })`
manages every `services[]` entry as a sidecar and reverse-proxies the
`proxyDashboard` one as the app's UI: the lifecycle contract on `$APP_PORT`
(`listen()`), an auth-injecting HTTP+WS proxy, `ensureAll()` /
`isRunning(name)` / `teardownAll()` / `containerName(name)`. Guide:
[Bring-your-own-runtime apps](/docs/bring-your-own-runtime).

`mode` decides who runs the containers:

| `mode` | Who runs them | Needs |
|---|---|---|
| `'os'` (recommended) | the OS, via `osSidecars()`; each service spawned as `{ template: service.name, takeover: true }`, waiting for its `readiness` when declared. `onSeed` throws, use `services[].seed`. | `sidecars.spawn` |
| `'docker'` (default) | the SDK, over the docker socket ([app-managed](/docs/sidecars/app-managed)) | the `docker` tool |
| `'auto'` | `'os'` when there is no docker socket but a token, else `'docker'` | either |

Moving an app from `'docker'` to `'os'`:
[Migrate to OS-managed](/docs/sidecars/app-managed#migrate-to-os-managed).

### Next.js raw-runtime (`packages/app-sdk/src/runtime/next.ts`)

Adapters that make a Next.js app conform to the Aura lifecycle
contract. **(S)** server-only. Used by `com.aura.docs` (this app).

| Symbol | Purpose |
|---|---|
| `createNextLifecycleRoutes(impl?: Partial<{onCreate,onStart,onResume,onPause,onStop,onDestroy: () => void \| Promise<void>}>)` | Returns `{ POST }` for `app/api/lifecycle/[...hook]/route.ts`. |
| `createNextHealthRoute()` | Returns `{ GET }` for `app/api/lifecycle/health/route.ts`. |
| `auraIdentityHeaders()` | Returns `{ 'X-Aura-App-Id', 'X-Aura-Instance-Id' }` — stamp from a Next middleware. |

```ts
// app/api/lifecycle/[...hook]/route.ts
import { createNextLifecycleRoutes } from '@aura/app-sdk/runtime/next';
export const { POST } = createNextLifecycleRoutes({
  onDestroy: async () => { /* teardown */ },
});

// middleware.ts
import { NextResponse } from 'next/server';
import { auraIdentityHeaders } from '@aura/app-sdk/runtime/next';
export function middleware() {
  const res = NextResponse.next();
  for (const [k, v] of Object.entries(auraIdentityHeaders())) res.headers.set(k, v);
  return res;
}
export const config = { matcher: '/(.*)' };
```

For other frameworks: roll a 6-line equivalent — middleware that
stamps the identity headers from `process.env` onto every response,
plus a `GET /api/lifecycle/health` returning the identity body.
Lifecycle hooks can default to no-op `{ ok: true }` JSON.
