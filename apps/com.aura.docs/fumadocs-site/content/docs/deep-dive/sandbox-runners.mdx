---
title: Sandbox runners
description: How ProotRunner + ContainerRunner spawn an app — entrypoints, bind mounts, tools allowlist, identity health check.
---

**TL;DR.** Two `SandboxRunner` implementations, one interface. Both spawn
a bash entrypoint with `$APP_PORT`, `$APP_ID`, `$APP_INSTANCE_ID`, `$OS_API_BASE`,
`$AURA_LAYER_TAG`, and `$PATH` (prepending `/aura/my-tools` for the
per-instance allowlist). They differ in two places: **isolation primitive**
(ptrace vs kernel namespaces) and **spawn cost** (~3 ms vs ~80-150 ms). Both
poll `/api/lifecycle/health` after spawn and verify identity.

Source of truth:
- `packages/core/src/app-manager/ProotRunner.ts`
- `packages/core/src/app-manager/ContainerRunner.ts`
- `packages/core/src/app-manager/SandboxRunner.ts` (the interface)

## The interface

Both runners expose the same shape:

```ts
interface SandboxRunner {
  spawn(instanceId, appId, port, manifest):     Promise<number>;  // returns pid
  callLifecycle(instanceId, hook):              Promise<void>;
  callOptionalLifecycle(instanceId, hook, body): Promise<unknown | null>;
  kill(instanceId):                             Promise<void>;
  forceKill(instanceId):                        void;            // SIGKILL
  onExit(instanceId, callback):                 void;
  getHost(instanceId):                          string | null;
  getPort(instanceId):                          number | null;
  listOrphanRecords?():                         Promise<…[]>;    // ContainerRunner only
  registerAdopted?(rec):                        void;             // ContainerRunner only
}
```

The AppManager picks which runner per spawn from `manifest.sandbox`:

```ts
const runner = this.runners[manifest.sandbox] ?? this.runners['proot'];
```

`ContainerRunner.listOrphanRecords()` is how containers survive a shell
restart: sibling containers tagged `aura-*` get re-adopted at boot.

## The synthesised entrypoint

When an app doesn't ship its own `entrypoint.sh`, the runner synthesises
one. Identical in spirit between runners, only `node_modules` discovery
differs:

```bash
set -e
export PORT="${APP_PORT:-4001}"
if [ ! -d node_modules ] && [ ! -d /workspace/node_modules ]; then
  npm install --prefer-offline 2>&1 || npm install
fi
ASTRO="node_modules/.bin/astro"
[ -x "$ASTRO" ] || ASTRO="/workspace/node_modules/.bin/astro"
exec "$ASTRO" dev --host 0.0.0.0 --port "$PORT"
```

For `runtime: 'raw'` apps (Next, SvelteKit, Go, anything), the runner
**requires** an explicit `entrypoint.sh` and throws if it's missing:

> `[ProotRunner] app 'com.aura.docs' has runtime: 'raw' but no entrypoint file at /workspace/apps/com.aura.docs/entrypoint.sh`

## Environment variables passed to every child

| Var | Set by | Meaning |
|---|---|---|
| `APP_ID` | runner | manifest.id |
| `APP_INSTANCE_ID` | runner | `appId` (single) or `appId-N` (multi) |
| `APP_PORT` | runner | allocated by `PortAllocator` |
| `OS_API_BASE` | runner | usually `http://localhost:3000` |
| `AURA_LAYER_TAG` | runner | `[proot+ctnr]` for PRoot, `[ctnr]` for container, `[host]` for outside |
| `PATH` | runner | prepends `/aura/my-tools` so the manifest's `tools[]` allowlist wins |
| `AURA_INSTANCE_TOKEN` | runner | bearer for the token-gated routes — see [Instance tokens](#instance-tokens) |

The bashrc snippet at `/os/bashrc.aura.sh` annotates the interactive prompt
with `$AURA_LAYER_TAG`, which is how `aura info` and the terminal
prompt know which layer they're in.

## ProotRunner — the cheap one

PRoot is a ptrace-based filesystem sandbox. It rewrites file-access
syscalls so the child sees a virtual rootfs, but it shares the host's
kernel, PID space, and network. ~3 ms spawn. Weak isolation — treat
apps as cooperating, not adversarial.

### Bind mounts (`buildProotArgs`)

```
--rootfs=<base-rootfs>           the shared base image (Debian)
--bind=/workspace:/workspace     the full monorepo
--bind=<dataDir>:/data           per-instance data
--bind=/proc                     host /proc
--bind=/dev                      host /dev
--bind=/tmp                      host /tmp (shared with siblings)
--bind=/etc/resolv.conf          host DNS
--bind=<sharedHome>:/root        per-user home (shared across apps)
--bind=<toolchainDir>:/aura/all-tools
--bind=<perInstanceToolsDir>:/aura/my-tools   the allowlist
--bind=/var/run/docker.sock:...  only if 'docker' in tools[] (or wildcard)
```

The two-dir tools layout (`all-tools` + `my-tools`) is the cap mechanism.
`/aura/all-tools/` mirrors the toolchain registry. `/aura/my-tools/`
holds symlinks ONLY for entries in `manifest.tools[]`. PATH inside
the sandbox is `/aura/my-tools:<inherited>`. So `tools: ["bash", "node"]`
means the child can `bash` and `node` but not `claude` even if claude is
installed on the host.

### The cap-grant fast path

`aura cap grant com.example.foo claude` writes the manifest, AppRegistry's
chokidar fires, AND the AppManager calls `provisionToolsDir(instanceId, manifest)`
again — re-running the symlink loop. The running child sees the new
binding within a tick without a respawn, because `/aura/my-tools/` is
the same bound directory.

### Identity gate at spawn (`waitHealthy`)

After spawn the runner polls `/api/lifecycle/health` (with basePath
respected for raw apps via `lifecyclePath(manifest, instanceId, 'health')`).
The response body MUST include `appId` and `instanceId` matching the
spawn. If they don't match → port squatter detected, spawn fails loud:

> `[ProotRunner] com.aura.foo on port 4003: health identity mismatch (expected appId=com.aura.foo, got appId=com.aura.bar). Another process is likely squatting this port.`

`verifyHealthIdentity` (line 427 of `ProotRunner.ts`) returns one of:
- `{ kind: 'match' }` — appId + instanceId both present and correct
- `{ kind: 'legacy' }` — both absent (older apps); warn but accept
- `{ kind: 'mismatch', claimedApp, claimedInstance }` — fail

`auraAppIntegration()` in `@aura/app-sdk` stamps both headers on every
response automatically. Raw-runtime apps use middleware (e.g.
`auraIdentityHeaders()` for Next via `@aura/app-sdk/runtime/next`).

## ContainerRunner — the strong one

Docker container sibling on the `aura-net` network. Each instance gets:
- its own PID/net/mount namespaces
- a hostname like `aura-com.aura.terminal-3` (proxy uses it as the upstream host)
- a sliced bind of `apps/<id>/` (the container sees ONLY its own app dir)
- shared bind of `packages/` (so workspace imports resolve)
- shared `aura-node-modules` volume so pnpm hoist works
- shared `aura-app-data` volume scoped to `<dataDir>/apps/<id>/`

### Spawn args (`buildDockerArgs`)

```
docker run -d --rm
  --name aura-<sanitized-instanceId>
  --hostname aura-<sanitized-instanceId>
  --network aura-net
  --env APP_ID=… --env APP_INSTANCE_ID=… --env APP_PORT=… --env OS_API_BASE=…
  --env AURA_LAYER_TAG=[ctnr]
  -v /workspace/apps/<id>:/workspace/apps/<id>       # sliced
  -v /workspace/packages:/workspace/packages          # shared
  -v /workspace/node_modules:/workspace/node_modules  # hoisted
  -v aura-app-data:/data
  -v /workspace/os/bashrc.aura.sh:/root/.bashrc:ro
  <BASE_IMAGE>                                        # default: aura-base
  <entrypoint argv>
```

The aura-net network is what lets the shell reach each app by
hostname. The shell joins the same network at compose time.

### Orphan adoption at shell boot

`listOrphanRecords()` walks `docker ps --filter name=aura-*` at AppManager
init. For each surviving container it:
- parses `APP_ID` / `APP_INSTANCE_ID` from env
- inspects the container's pid + port
- re-registers as state `resumed` (record and lifecycle FSM) without
  re-running `onCreate/onStart/onResume`
- re-learns the instance's token nonce from its `aura.token.nonce` label

This is why `docker compose restart aura-shell` doesn't kill your
running terminal/console — the containers outlive the shell.

PRoot apps don't survive: they're direct children of the shell node and
die with it. Only `sandbox: 'container'` apps adopt.

After adoption, in this order (`AppManager`):

1. `SidecarManager.reconcile(liveInstanceIds)` walks
   `docker ps -a --filter label=aura.managed=os`. A sidecar whose
   `aura.parent` instance is gone is removed; every other one has its token
   nonce re-registered and its mount inheritance put back into the fan-out
   view. Nothing is recreated.
2. `MountManager.reconcile(instances + liveConsumerKeys())` adopts or reaps
   binds. It needs the sidecars' consumer keys (`<instance>--<sidecar>`) to
   tell a live sidecar's binds from a dead one's; a bind on a sidecar that it
   never declared itself is re-marked `inherited`.
3. `PortExpose.reconcile`.

### Instance tokens

`InstanceTokens` (`packages/core/src/app-manager/InstanceTokens.ts`) gives each
instance — and each OS sidecar with `inheritIdentity` — a bearer:

```
aura1.<base64url {i: instanceId, s?: sidecar, n: nonce}>.<base64url HMAC-SHA256>
```

- The HMAC key is 32 random bytes in `<data>/aura/secrets/instance-token.key`
  (0600, created on first use). Rotating it revokes every token.
- The **nonce** is fresh per spawn and stored where the container lives: the
  `aura.token.nonce` label on an app container, the spec label on an OS
  sidecar. Nothing to persist; a shell restart re-learns nonces from
  `docker inspect`.
- A token verifies only while its nonce is current — a recycled instance id
  or a deleted sidecar invalidates every older token.
- Injected as `AURA_INSTANCE_TOKEN`, after OS Context env so a context key
  can't replace it. Instances started before tokens existed have none until
  their next start.

Both runners inject it (PRoot instances get one too, though the sidecar
routes then answer 409: OS sidecars need a container sandbox).

Only the sidecar routes require it today. `sidecarGate` in
`packages/shell/src/lib/instanceAuth.ts` runs the same prelude for each:
instance exists (404) → bearer present and `verify()`-able (401) → claims
belong to the URL's instance (403) → the instance's **app** holds the
route's permissions (403) → container sandbox (409). A sidecar calling with
its own token passes as `caller.sidecar`, which becomes the `owner` of what
it spawns.

Anything holding the docker socket can read another container's env and with
it the token — the socket is host root anyway, so that adds no exposure.

### OS-managed sidecars

`SidecarManager` (`packages/core/src/app-manager/SidecarManager.ts`) starts
containers on an app's request ([Sidecars](/docs/sidecars)). The rules of
what may be asked live, pure and docker-free, in `sidecar-spec.ts`:

- `parseSpawnRequest` whitelists the request keys (`template`, `name`,
  `suffix`, `image`, `env`, `envInherit`, `command`, `mounts`, `replace`,
  `takeover`, `wait`); anything else is a 400 naming the allowed ones.
- `resolveSidecarSpec` merges request over template and applies the gates:
  `image` ≠ template → `sidecars.anyImage`; `privileged` / `capabilities` /
  `devices` / `publish` → `sidecars.privileged`; `inheritDockerSocket` →
  the app's own `tools[]` must grant docker; `volume` / `subpath` → 400.
  Volumes resolve to `aura-<appId>-<vol>` if that legacy volume exists (only
  for the template-named sidecar), else a volume-subpath of the app-data
  volume at `<app data>/.sidecars/<sidecar or template if shared>/<vol>`.
- `specHash` is a sha256 over the canonical JSON (keys sorted at every
  level) of the resolved spec, first 16 hex chars.

`spawn(instanceId, req, caller)` then, serialised per container name:

0. A sidecar caller (its own token) without the app's `sidecars.manageAll`
   may only touch names in its own subtree (owner chain via
   `aura.sidecar.owner`) → 403; the same check runs before get, exec, logs,
   delete and mounts (`authorize`), and `list` filters by it.
1. `docker inspect` the name. App-managed container (no `aura.managed=os`)
   → 409, unless `takeover` and its `aura.parent` is this instance. OS
   sidecar with an equal hash and `running` → **adopt**: re-register its
   nonce, track it, re-apply its mounts (idempotent), return `created: false`.
   A different hash with `replace: false` → 409. Otherwise remove it (own
   mount declarations stay) and continue.
2. New name: count the instance's **running** OS sidecars against the limit
   → 429. The limit is the OS setting `os:sidecars.maxPerInstance` in
   Valkey, else `AURA_SIDECAR_MAX_PER_INSTANCE`, else 32.
3. `ensureImage`: `docker pull` if missing, 10 min timeout, concurrent pulls
   of one image share one promise.
4. Create the volume subpath dirs and, with `mounts.own` or inheritance,
   the mount root `aura/mounts/<instance>--<name>`. A template with `tools`
   gets its own tools dir filled now, before `docker create` (see
   [Tools of an OS sidecar](#tools-of-an-os-sidecar)).
5. Env: `envInherit` from OS Context, falling back to the app container's
   env (`docker inspect aura-<instanceId>`), then the spec's `env`.
6. `seed`, if declared and not seeded yet. The marker is keyed by the data:
   `.sidecars/.seeded/<sha of the resolved volume subpaths>` (`name-<name>`
   without volumes); a legacy per-app docker volume counts as seeded; spawns
   sharing a marker are serialised. Otherwise: a `docker run --rm` of the image with the volumes and env,
   labelled `aura.mount=1` (hidden from listings) and `aura.parent` (reaped
   if the instance dies mid-seed). Marker written on success.
7. With `inheritIdentity`, mint a token for `<instance>--<name>`.
8. `docker create` + `docker start`. Identity env is appended last so a
   template key can't overwrite it. With `inheritHome` the user home volume
   subpath is mounted at `/home/aura` and `HOME=/home/aura` set after the
   template env (the flag is absent from the spec otherwise, so existing
   spec hashes don't change). Then a 400 ms still-alive check: a
   container that died is removed and the spawn fails with its last 20 log
   lines.
9. Track it for fan-out, `MountManager.reapplyConsumer` (own declarations
   restored, then the parent's mounts minus `exclude`, `forceRo` applied),
   and with `wait.port` poll TCP until the port answers (default 60 s), with
   `wait.ready` poll `readiness.path` until it answers HTTP below 500.
10. Notify AppManager (`changed`), which refreshes its sidecar cache at once.

`prePull` templates are pulled on `app:installed` and once at shell start
(background, missing images only).

Docker is the source of truth; the in-memory state is only the fan-out map
and token nonces, both rebuilt by `reconcile`. Every sidecar carries its
record in labels:

| Label | Value |
|---|---|
| `aura.parent` / `aura.app` / `aura.service` | instance, app, sidecar name; the same as app-managed sidecars, so the existing reaper removes them on stop and crash and orphan adoption skips them |
| `aura.managed` | `os` |
| `aura.sidecar.template` / `aura.sidecar.owner` | template, and the sidecar that spawned it (or `-`) |
| `aura.sidecar.spec` | JSON: name, template, image, spec hash, token nonce, port, mount view (`own`, `inherit`, `exclude`, `forceRo`), owner, `ownTools` (only when set), created-at |

`remove(instanceId, name)` deletes the owned children first (recursively,
by `aura.sidecar.owner`), then `MountManager.forgetConsumer` (binds,
declarations, mount root), `docker rm -f`, its own tools dir and runtime
tool grants, and the token nonce.

All docker calls are async `execFile`s with their own timer (the docker CLI
forwards SIGTERM to an exec'd process and then exits cleanly, so execFile's
own `timeout` would report a timed-out exec as success); that is where
`timedOut` comes from.

#### Sidecars as mount consumers

`MountManager` treats `<instanceId>--<sidecar>` as a consumer like any
instance: container `aura-<inst>--<sc>`, mount root `aura/mounts/<inst>--<sc>`,
never the legacy `/data/.mnt` root (a sidecar without a root gets a 409).
Own mounts are declared and persisted like an app's. Inherited ones are
derived: a mount added to or removed from the instance is queued onto a
serial fan-out chain that mirrors it into every `fanoutTargets(instance)`
entry (live OS sidecars with `inherit`), honouring `exclude` and `forceRo`.

`verify()` reads the consumer's `/proc/self/mountinfo` with `docker exec cat`.
A sidecar image without `cat` is read by a helper container in its PID
namespace (`--pid=container:<sidecar>`, `cat /proc/1/mountinfo`). If neither
works, a read-only mount into a sidecar is refused and rolled back rather
than handed out unverified.

#### Tools of an OS sidecar

`inheritTools` mounts the app's own dir (`aura/runtime/<instance>/tools`).
A template with `tools` instead gives each sidecar a dir of its own,
`aura/runtime/<instance>--<sidecar>/tools`, mounted read-only at
`/aura/my-tools` with the same PATH / packages / profile.d args
(`toolArgs(dirKey)`). The spec only carries `ownTools: true` (present only
when set, so older specs keep their hash); the list is applied live.

`effectiveSidecarTools` (`sidecar-tools.ts`, pure) resolves the template
list and the runtime grants **separately** with `resolveToolBinaries`
(markers, helper binaries), unions them and intersects with the app's
resolved `tools[]`; named tools the app lacks come back as `ignored`.
`provisionAllowlist` then refills the dir with the effective names, in
place (docker binds the dir by inode), so a running sidecar sees changes
without a recreate. It runs before `docker create`, on adopt, in
`reconcile` for live parents, on `grantTools` / `revokeTools`, and from
`AppManager.refreshInstanceTools` (`osSidecars.refreshTools(instance)`)
after an app's `tools[]` or a template's `tools` changed.

Runtime grants are persisted in `aura/runtime/.state/<instance>--<sidecar>.tools.json`,
so a recreated sidecar gets them back. `remove`, `reconcile` reaping and a
deliberate stop / kill (`SidecarManager.forget`) delete the dir and the
file; a crash (`removeAll`) keeps them for the respawn, like mount
declarations.

## Tools allowlist mechanics

```
manifest.tools: ["bash", "node", "git"]
                 │
                 ▼
provisionToolsDir(instanceId, manifest)
   creates /data/aura/runtime/<instanceId>/tools/
   then symlinks:
     bash → /aura/all-tools/bash
     node → /aura/all-tools/node
     git  → /aura/all-tools/git
                 │
                 ▼ (PRoot bind mount)
   /aura/my-tools/* visible inside the sandbox
                 │
                 ▼ (PATH prepend)
   $PATH = "/aura/my-tools:${inherited}"
```

`'*'` in `tools[]` mirrors the entire `/aura/all-tools/` directory.
`'claude-code'` symlinks to `claude` (historical name change preserved).

## Spawn flow comparison

```
PRoot                                 Container
─────                                 ─────────
resolveEntrypoint()                   resolveEntrypoint()
provisionToolsDir()                   buildDockerArgs()
buildProotArgs()                      execFileSync('docker', args)
spawn('proot', args, env)             attach `docker logs -f` for stdio
processes.set(instanceId, {...})      docker inspect → pid
waitHealthy(...)                      tracked.set(instanceId, {...})
                                       watcher = spawn('docker', ['wait', ...])
                                       waitHealthy(...)
~3 ms                                 ~80-150 ms
```

## Process exit + cleanup

Both runners call the per-instance `exitCb` registered by AppManager
when their child exits unexpectedly. AppManager flips the instance to
`'error'` state and emits `app:crashed` on the event bus.

For ProotRunner: `child.on('exit')` fires. The runner sets `processes.set(instanceId, …)` → null and reports.

For ContainerRunner: a `docker wait <containerId>` watcher prints the
exit code; the runner parses + reports. `expectingKill: true` on the
tracked record suppresses the callback (the AppManager just did
`docker kill` itself).

On stop, kill and crash:

- the instance's siblings are reaped by their `aura.parent` label (app- and
  OS-managed alike, `reapSiblingsOf`);
- `MountManager` unmounts the instance's binds **and** its sidecars' binds
  (a leaked bind pins the source filesystem and the app-data volume);
- `InstanceTokens.forgetInstance` drops the nonces of the instance and every
  `<instance>--*` sidecar, so their tokens stop verifying;
- `SidecarManager.removeAll` clears the fan-out view; on a deliberate
  stop / kill `SidecarManager.forget` also drops the sidecars' own tools
  dirs and runtime tool grants.

A deliberate stop/kill also forgets the mount declarations of the instance
and its sidecars and removes the sidecars' mount roots (`MountManager.forget`);
a crash keeps the declarations so the respawn gets its mounts back. OS
sidecars are **not** respawned by the OS: the respawned app spawns them again,
and their own mounts are restored from the kept declarations.
