Nexus is how apps get on and off AuraOS. It's both the **distribution
layer** (resolve → fetch → validate → install) and the **app store** (a
catalog aggregated across every registered source). Once Nexus installs an
app, the AppManager runs it like any other — nothing in the app SDK depends
on Nexus, and apps never call into it.

To ship your own app, jump to **[Publish an App](./publish-an-app)**. This
page covers the model and how to manage registries.

## Sources

Nexus aggregates apps from a set of **sources** you register. Each source is
exactly one strict kind — the store never guesses:

| Kind | What it is | Distributes |
|---|---|---|
| `oci` | An OCI registry. Self-describing: apps are pushed as annotated artifacts under the `aura-apps/<id>` repo, and the store reads their metadata straight back. Can also be a pull `--mirror`. | Many apps |
| `git-index` | A git repo (or a direct `*.yaml` URL) hosting an `index.yaml` that lists many apps. Contains no app code itself. | Many apps |
| `git-app` | A git repo that **is** a single app (manifest at its root). | One app |

Two distribution forms follow: an **OCI artifact** (from an `oci` source or
an index entry's `oci` ref) or a **git repo** (a `git-app` or an index
entry's `git` ref). Sources are persisted in the shell KV store at
`os/nexus/sources`.

### The local registry

Every OS ships with `com.aura.registry` — a [zot](https://zotregistry.dev)
OCI registry running as a system service at
`http://aura-com.aura.registry:4090`. It's pre-registered as the source
`local` (priority 0), so you can publish and install end-to-end with no
external account. It's the default target for `aura nexus app publish`.

## Managing sources

```bash
aura nexus registry list                          # every source: kind, url, priority
aura nexus registry remove <name>                 # drop a source

# Add an OCI registry (a private mirror, a corporate ghcr.io, …):
aura nexus registry add myreg https://reg.example.com --kind oci

# Add a git-index catalog (a repo with an index.yaml of many apps):
aura nexus registry add community github.com/you/aura-catalog --kind git-index

# Add a single-app git repo:
aura nexus registry add hello github.com/you/hello --kind git-app
```

`--priority <n>` orders sources (lower wins when the same app id appears in
several); `--mirror` (oci) probes that registry first for any ref;
`--ref <branch|tag>` pins a git source. When you add a `git-index` or
`git-app`, Nexus fetches/clones it once to validate it before saving.

Run your own store by standing up any OCI registry (or hosting an
`index.yaml` in a repo) and registering it here — no AuraOS-specific server
needed.

A **private** registry takes a login, and a store can describe itself so
customers only type its address:

```bash
aura nexus registry add apps.acme.com             # by address (/.well-known/aura-store.json)
aura nexus registry add acme https://registry.acme.com --username me   # asks for the password
aura nexus registry login acme                    # change the login later
```

The password is stored encrypted and is never shown again. See
**[Private stores](./private-stores)** for both sides: adding one, and
running one for your customers.

The **Sources** tab of the Nexus app does the same: add, **edit** (alias,
URL, priority, mirror, git ref) and remove sources, and add or change a
login. Renaming a source changes its alias — publish targets that use the
old name (`--to`, a manifest's `publish.registry`) must follow.

## Pre-registered sources

An install can ship sources that exist from its first boot — say, your
company registry under the alias `acme`, so `aura nexus app publish --to acme`
works right away. Nexus reads seeds from, in rising precedence:

| Where | Meant for |
|---|---|
| `/etc/aura/nexus/sources.d/*.json` | shipped with the install or image (read-only) |
| `/data/nexus/sources.d/*.json` | the admin of this machine (persists) |
| `AURA_NEXUS_SOURCES` | the environment: JSON, or a path to a JSON file |

Files apply in name order; for the same alias the later one wins. Each holds
a list (or `{ "sources": [ … ] }`) of entries:

```json
[
  { "name": "acme", "url": "https://registry.acme.com", "priority": 5,
    "username": "ci", "passwordFile": "/run/secrets/acme-registry" },
  { "name": "corp-catalog", "kind": "git-index", "url": "github.com/acme/aura-catalog",
    "policy": "managed" }
]
```

| Field | |
|---|---|
| `name` | the alias — required |
| `kind` | `oci` (default), `git-index` or `git-app` |
| `url` | required |
| `priority` | lower is checked first (default 10) |
| `mirror`, `appRepoPrefix` | oci only |
| `ref`, `repo` | git sources: branch/tag, and the submission repo of an index |
| `policy` | `seed` (default) or `managed` |
| `username` + `password` / `passwordEnv` / `passwordFile` | login of a private oci registry |

The two policies:

- **`seed`** — the source is added once and then belongs to the user: edits
  and removal in Nexus stick. Only a change of that entry in the seed applies
  it again. Nexus shows it as *pre-registered*.
- **`managed`** — the seed owns it: it is enforced on every boot, shown
  🔒 locked in Nexus (no edit, remove or login change there), and removed
  when it disappears from the seeds.

A login is sealed into the OS-only secret store like one entered by hand; the
sources config keeps only the username. `passwordEnv` (the name of an
environment variable) or `passwordFile` (e.g. a Docker secret) keep the
password out of the JSON; an inline `password` works too, but then the file
holds a secret in plain text — keep its permissions tight.

Seeds are applied after each shell boot. After editing a file, press
**RE-APPLY SEEDS** on the Sources tab (or `POST /api/nexus/sources/seeds`) —
no restart needed. The same tab lists the files found, what they declare and
any problems; `GET /api/nexus/sources/seeds` returns it as JSON.

## Installing

```bash
aura nexus app install <ref>            # resolve + fetch + validate + install
aura nexus app list                     # what's installed (id, version, scope, source)
aura nexus app info <ref>               # dry-run: resolved address + permission preview
aura nexus app update [<id>|--all]      # re-resolve the stored ref, reinstall if changed
aura nexus app uninstall <id> [--purge] # stop instances, remove (purge also wipes /data)
aura nexus search [<q>] [--refresh]     # search the aggregated catalog
```

`<ref>` can be a store id, a registry ref, a git URL, or a local path — the
resolver dispatches on the shape, no flags needed:

| Shape | Example | Routed to |
|---|---|---|
| Store id (`<reverse.domain>[@channel]`) | `com.example.hello@stable` | catalog → OCI or git |
| OCI ref | `oci://ghcr.io/u/foo:1.2.3`, `host/u/foo@sha256:…` | OCI (via `oras`) |
| Git URL (optional `#ref`) | `github.com/u/repo#v1.2.3` | git |
| Local path | `./apps/com.example.foo`, `/abs/path` | filesystem |

Installs default to the **global** [scope](./scopes); pass `--scope user`
for a per-user install. Full command flags live in the
[CLI Reference](./cli-reference).

## Same id, same app?

The store compares the app's `id` *and* its `originId`
([what they are](./develop-an-app#id-and-originid)). An install never replaces
an installed app just because the ids match:

| Situation | What happens |
|---|---|
| Same app (`originId`), from the source it was installed from | Normal update. |
| Same app, offered by **another** source | Asks: update the installed app, which then follows the new source, or install an independent copy. |
| Same `id`, **different** app | Asks: install it under another id. The installed app is kept. |
| Same app under **another** local id | Asks: update that app (it keeps its local id), or install a copy. |
| Neither matches | Normal install. |

Interactively, `aura nexus app install` / `update` asks. In scripts, answer
with `--update-existing` (alias `--switch-source`), `--as <appId>` or
`--copy [appId]`. A copy gets a new id and a new `originId` and never updates
from the source.

Over the API, `/api/nexus/install` (and `/update/<id>`) reply
`{ needsIdentityChoice, conflict }`. Send the install again with
`identity: { action, appId? }`, where `action` is one of `conflict.choices`.

## Permission gating

Before an install lands, Nexus diffs the incoming manifest's `permissions[]`,
`tools[]`, and `dataProvider` against the currently-installed version. Pure
code updates go through silently; anything that **adds** a permission, a
tool, or a content-provider authority pauses and asks for approval. Pass
`-y` / `--yes` to skip the gate (right for CI, never for user-driven
installs).

## The pipeline

Every install walks the same stages, driven as an async generator
(`NexusManager.install`) so the CLI and the shell UI consume the same event
stream:

```
ref  →  Resolver  →  Fetcher  →  Validator  →  Identity  →  PermissionDiff  →  Installer
                                                  ↓                ↓
                                            (choice gate)   (approval gate)
                                                     ↓
                                              install record
```

- **Resolver** classifies the ref and, for store ids, looks it up in the
  aggregated catalog.
- **Fetcher** pulls the source into staging — `oras pull` for OCI, `git
  clone` for git, copy for local.
- **Validator** runs the manifest schema and rejects anything malformed.
- **Identity** matches the app against installed ones by `id` + `originId`
  ([above](#same-id-same-app)) and, when chosen, gives it another local id.
- **PermissionDiff** computes the approval gate above.
- **Installer** lands the app into the target scope's `appsDir` and writes an
  install record; the AppRegistry picks it up and the app becomes launchable.

For the internals, see the [Nexus pipeline deep-dive](./deep-dive/nexus-pipeline).
