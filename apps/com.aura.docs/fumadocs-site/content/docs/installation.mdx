AuraOS ships as one Docker image — `aura-shell` — that hosts the
desktop + AppManager + reverse proxy. Sibling app containers come up
on demand. You don't install per-app dependencies on the host.

## Prerequisites

- **Docker** + **docker compose** (Compose v2 syntax).
- A modern browser (anything with WebGL2 + ES2022 support; we test
  Firefox + Chromium).
- ~2 GB free disk space for the base image + workspace caches.
- (Optional, host-side dev) `pnpm` ≥ 9, Node ≥ 22 — only needed if
  you want to edit OS internals from the host instead of from inside
  an app sandbox.

## Run AuraOS

```bash
git clone https://github.com/<org>/aura.git
cd aura
docker compose up
```

That one command is the whole installation. The first run builds two
images and takes a few minutes; later boots take seconds:

- **`aura-shell`** — the desktop, AppManager and reverse proxy.
- **`aura-base`** — the image every `sandbox: "container"` app (and the
  OS's helper containers) runs from. Compose builds it first; the shell
  starts once it is there.

Open `http://localhost:3000` in your browser as soon as the containers
are up — you don't have to wait for the build to finish.

## First boot

A first start walks you through three stages, all in the browser:

1. **AuraOS is starting** — while the shell container installs its
   dependencies and builds every package, `:3000` serves a small page
   with the current step and the live log (`os/boot.sh`,
   `os/boot-splash.mjs`). It switches to the desktop by itself. If the
   build fails, the page shows the error; the container retries after a
   few minutes. The same log is in `/data/aura/boot/boot.log`.
2. **Setting up AuraOS** — on the desktop, a pinned notification
   follows the background work step by step: the app image, the app
   registry and SDK, and Aura Docs.
   A failed step shows its error and a **Retry** button. You can
   already look around while it runs.
3. **Welcome to AuraOS** — a getting-started checklist: unlock admin,
   install and log in to an AI agent, pick a theme, build your first
   app, read the docs. Its buttons open the right app, and the steps
   tick themselves off. Hide it whenever you like. See
   [Getting started](/docs/getting-started).

If the shell ever comes up without `aura-base` later (for example
after a `docker image prune`), the **Setting up AuraOS** notification
comes back while it rebuilds it, and container apps start when it is
done.

`autoStart` apps spawn before you click anything — today **Aura
Docs** (this site), plus the services: the app registry and the Shell
Daemon. Open the launcher (`⣿` in the dock, or
`Ctrl+Alt+Space → Enter → launcher icon`) to see every installed app.
Click an icon, the sandbox spawns, the iframe loads. First-spawn cold
start is ~1-3 s; subsequent launches hit the warm pool when present.

## Troubleshooting

**`pull access denied for aura-base, repository does not exist`.**
`aura-base` isn't on any registry — it is built locally from the
`Dockerfile`, and Docker tried to download it because it wasn't there.
`docker compose up` builds it; to build it by hand run
`docker compose build aura-base`. A running shell also builds it on its
own (see above); `GET /api/admin/first-boot` shows that build's state
and `?log=1` its log.

**`GET /api/proxy/com.aura.foo/ → 503`.** The app is mid-spawn. The
proxy returns 503 until the AppManager's health probe passes. Wait
2-3 s and reload the iframe; the skeleton in the slot will swap to
the real content as soon as health is green.

**Nothing in the launcher.** Check `docker logs aura-shell` for
`[AppRegistry] Loaded: <id>` lines — if your app isn't in the list,
its manifest probably failed schema validation. Run
`aura dev validate --all` from inside the master container
(`aura jump --master` from the Terminal app); `aura get apps` lists what
did load.

**Apps stuck in `error` state.** The Process Manager (`Ctrl+Alt+M`)
shows lifecycle state per instance. Hit the **Kill** button to
SIGKILL, then **Launch** to respawn cold. From the Terminal app:
`aura ps` shows the same states, `aura kill inst <instanceId>` then
`aura run <appId>` does the same reset.

**Port in use.** The shell binds `:3000` on the host. Edit
`docker-compose.yml` to map a different host port if needed; the
shell's internal port stays 3000 either way.

See [Core Concepts → Proxy + iframe](/docs/core-concepts#proxy-and-iframe)
if you want the gory details of how requests flow, and
`aura status` (or [Troubleshooting](/docs/troubleshooting)) for a quick
health check.
