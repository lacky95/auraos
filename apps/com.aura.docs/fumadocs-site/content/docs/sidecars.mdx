title: Sidecars & inheritance
description: Run a second runtime (database, agent, any foreign image) next to your app — started by the OS on request, with its own mounts — and choose exactly how much of your app it inherits.
---

**TL;DR.** A **sidecar** is a container that runs next to your app instance
on `aura-net`. The official way to get one: declare it as a **template** in
`services[]`, then ask the OS to start it through the SDK
(`osSidecars().spawn(...)`). The OS does the `docker run`, so **your app
needs no docker tool** — only the `sidecars.spawn` permission. You can start
as many as you like at runtime, give each one cross-app mounts of its own,
and run commands in it.

The older way — your app runs docker itself through the SDK or `docker run`
— keeps working unchanged (see [App-managed sidecars](#app-managed-sidecars)).

Source of truth: `packages/core/src/app-manager/SidecarManager.ts` (the OS
side), `sidecar-spec.ts` (what may be asked), `packages/app-sdk/src/os-sidecars.ts`
(the client). Related: [Cross-App Mounts](/docs/cross-app-mounts),
[Bring-your-own-runtime](/docs/bring-your-own-runtime).

## Two ways to run a sidecar

| | OS-managed (official) | App-managed |
|---|---|---|
| Who runs `docker run` | the OS, on your request | your app (SDK `mode: 'docker'`, or raw docker) |
| Your app needs | `sidecars.spawn` permission | the `docker` tool — i.e. host root |
| What can run | your `services[]` templates (any image with `sidecars.anyImage`) | anything |
| Mounts of its own | yes, at runtime (`sidecars.mounts`) | no — only the shared `inheritMounts` root |
| exec / logs | OS API (`sc.exec`, `sc.logs`) | your own `docker exec` |
| `aura get sc` shows | `MANAGED os` | `MANAGED app` |

Both kinds are named `aura-<instanceId>--<name>`, labelled
`aura.parent=<instanceId>`, reachable at that name on `aura-net`, and removed
with their instance on stop **and** on crash.

## Quick start

```jsonc
// app.manifest.json
{
  "sandbox": "container",
  "tools": ["bash", "node"],                 // no "docker"
  "permissions": ["sidecars.spawn"],
  "services": [
    { "name": "db", "image": "postgres:17", "port": 5432,
      "env": { "POSTGRES_PASSWORD": "dev" },
      "volumes": [{ "name": "data", "target": "/var/lib/postgresql/data" }] }
  ]
}
```

```ts
import { osSidecars } from '@aura/app-sdk/os-sidecars';

const sc = osSidecars();                       // instance id + token come from the env
const { sidecar } = await sc.spawn({ template: 'db', wait: { port: true } });
// → postgres at `${sidecar.host}:5432`, i.e. aura-<instanceId>--db:5432

const r = await sc.exec('db', ['psql', '-U', 'postgres', '-c', 'select 1']);
console.log(r.exitCode, r.stdout);
```

Prefer the `createSidecars` shape you already know? It takes a mode:

```ts
import { createSidecars } from '@aura/app-sdk/sidecars';
const host = createSidecars({ appId, instanceId, appPort, services, mode: 'os' });
await host.ensureAll();      // each service → spawn({ template: service.name })
```

`osSidecars()` is server-side only: the token it sends lives in your app's
env and must never reach a browser.

## Templates and requests

Every OS sidecar is spawned from a `services[]` entry of the calling app. A
request picks the template and may change **only**:

| Field | Meaning |
|---|---|
| `name` / `suffix` | Sidecar name (default: the template name), or `<template>-<suffix>`. `^[a-z][a-z0-9-]{0,47}$`. |
| `env` | Merged over the template's `env` (request wins). |
| `envInherit` | Extra names to inherit, merged with the template's list. |
| `command` | Replaces the template's command. |
| `mounts` | `{ own?, inherit? }` — see [Mounts](#mounts-of-a-sidecar). |
| `image` | A different image — needs `sidecars.anyImage`. |
| `replace` | Default `true`: a running sidecar with a different spec is recreated; `false` → 409. |
| `takeover` | Replace your own app-managed container of the same name (migration). |
| `wait` | `{ port: true, timeoutMs? }` — answer only once the template's port accepts TCP. |

Anything else (`volumes`, `privileged`, `user`, …) is a 400: change the
template instead. That is the point — the manifest is what gets reviewed at
install time.

**Dynamic sidecars** are just requests with different names:

```ts
const job = await sc.spawn({ template: 'worker', suffix: jobId, env: { JOB_ID: jobId } });
// … aura-<instanceId>--worker-<jobId>
await sc.remove(`worker-${jobId}`);
```

Same name + same spec → the running sidecar is **adopted** (`created: false`);
a changed spec → it is recreated. So calling `spawn` on every app start is
safe and cheap.

## Permissions

All four are enforced — an app without them gets a 403.

| Permission | Allows |
|---|---|
| `sidecars.spawn` | Spawn, list, get, delete, exec, logs of the app's own OS sidecars, from its templates. |
| `sidecars.anyImage` | An `image` that is not the template's. |
| `sidecars.privileged` | Templates with `privileged`, `capabilities`, `devices` or `publish` — **even though the template declares them**: the OS path must not turn into a privilege route for an app without a docker socket. |
| `sidecars.mounts` | Manage the own mounts of the app's sidecars. Also needs `apps.mount` — a sidecar never sees an app its app couldn't mount. |

`inheritDockerSocket` additionally requires the app itself to hold the
`docker` tool: a sidecar never exceeds its app.

## Inheritance

Opt-in per template, default off.

| Template field | OS-managed sidecar gets | App-managed sidecar gets |
|---|---|---|
| `inheritIdentity` | `AURA_APP_ID`, `AURA_INSTANCE_ID`, `AURA_SIDECAR_NAME`, `AURA_OS_URL`/`OS_API_BASE`, `AURA_SHELL_HOSTNAME`, and **its own** `AURA_INSTANCE_TOKEN` | the app's identity vars and the app's token (it acts as the app) |
| `inheritPermissions` | `AURA_PERMISSIONS=<app permissions>` | same |
| `inheritTools` | the app's granted tools at `/aura/my-tools` (+ PATH, workspace packages, login-shell PATH drop-in) | same |
| `inheritMounts` | the app's cross-app mounts at `/mnt/aura`, **mirrored live** into its own mount root | the app's mount root, shared |
| `inheritDockerSocket` | the host docker socket — only if the app has the `docker` tool | the socket, if the app has one |
| `envInherit: [...]` | values from OS Context, falling back to the app container's env | values from the controller's `process.env` |

Missing `envInherit` names are skipped; an explicit `env` entry wins.

## Mounts of a sidecar

A sidecar spawned with `mounts.own` or `inheritMounts` gets **its own** mount
root at `/mnt/aura` (`aura/mounts/<instanceId>--<name>` on the app-data
volume). Two kinds of mounts land there:

- **Own mounts** — added at runtime by the app, declared and restored like an
  app's ([Cross-App Mounts](/docs/cross-app-mounts)). Needs
  `sidecars.mounts` + `apps.mount`, and a sidecar spawned with `mounts: { own: true }`.
- **Inherited mounts** — the app's own cross-app mounts, mirrored in. When
  the app mounts or detaches something, every inheriting sidecar follows,
  live. They are never declared on the sidecar; you detach them on the app.

```ts
// own mounts: per sidecar, at runtime
await sc.spawn({ template: 'agent', suffix: 'a1', mounts: { own: true } });
await sc.mounts('agent-a1').add('com.example.docs');               // ro
await sc.mounts('agent-a1').add('com.example.notes', { mode: 'rw' });
await sc.mounts('agent-a1').list();     // own + inherited, with `origin`
await sc.mounts('agent-a1').remove('com.example.docs');

// inherited: all of the app's mounts except one, capped at read-only
await sc.spawn({ template: 'agent', suffix: 'a2',
  mounts: { inherit: { exclude: ['com.example.secret'], mode: 'ro' } } });
```

`exclude` and `mode` are fixed at spawn time; respawning with a different
value recreates the sidecar (the spec changed). Read-only is verified inside
the sidecar after every bind — also for images without `cat`, through the
sidecar's PID namespace — and a mount that can't be verified read-only is
refused.

## exec and logs

```ts
await sc.exec('db', ['sh', '-c', 'pg_isready'], { timeoutMs: 5000 });
// → { exitCode, stdout, stderr, truncated, timedOut }
await sc.exec('db', ['psql', '-U', 'postgres'], { stdin: 'select 1;' });
await sc.logs('db', { tail: 100, since: '10m' });   // → { stdout, stderr }
```

`cmd` is an argv, not a shell string. Output is capped at 4 MiB per stream,
stdin at 64 KiB, the timeout at 10 minutes. A timed-out exec reports
`timedOut: true`. Interactive sessions are out of scope — for those, jump in:
`aura jump <app> --sidecar <name>`.

## Volumes and seeding

`volumes[]` of an OS sidecar live in the app's own data area:
`<app data>/.sidecars/<sidecar-name>/<volume>`, or one dir per template with
`"shared": true`. A pre-existing per-app volume `aura-<appId>-<volume>`
(left by the SDK docker path) still wins for the template-named sidecar, so a
service keeps its data when it moves to the OS path. `volume` / `subpath`
overrides are SDK-path only — the OS refuses them.

`seed: { command: [...] }` runs once before the first start, in the same
image with the same volumes and env (through the image's entrypoint); a marker
file in the sidecar's data dir keeps it from running again. It replaces the
SDK's `onSeed` callback.

## Lifecycle

- **Stop or crash of the instance** removes all its sidecars, their mounts
  and (on a deliberate stop) their mount declarations.
- **Shell restart:** OS sidecars keep running; the OS re-learns them from
  their labels — tokens, mounts, the fan-out — without recreating anything.
- **Grandchildren:** a sidecar with `inheritIdentity` can call the same API
  with its own token; what it spawns is labelled with it as owner and
  deleted together with it.
- **Limit:** 32 OS sidecars per instance (`AURA_SIDECAR_MAX_PER_INSTANCE`).
- **Name clash:** an app-managed container with the same name is never
  touched (409) — unless the request says `takeover: true` and it belongs to
  the same instance.

## Identity: instance tokens

The OS gives every instance a bearer at spawn, `AURA_INSTANCE_TOKEN`; the
sidecar routes require it (`Authorization: Bearer …`) and check that it
belongs to the instance in the URL. OS sidecars with `inheritIdentity` get a
token of their own. Tokens survive shell restarts and die with the container
they were minted for. The older routes (mounts, ports, …) still trust the
instance id in the URL. Details: [Sandbox runners](/docs/deep-dive/sandbox-runners#instance-tokens).

An instance started before tokens existed has none — restart it once.

## HTTP API

All under `/api/instances/:instanceId/`, token-gated, container sandboxes only.

| Route | Permission | Result |
|---|---|---|
| `POST sidecars` | `sidecars.spawn` | `{ ok, created, sidecar }` — 201 created, 200 adopted |
| `GET sidecars?view=managed` | `sidecars.spawn` | `{ sidecars: OsSidecar[] }` |
| `GET` / `DELETE sidecars/:name` | `sidecars.spawn` | `{ sidecar }` / `{ ok }` |
| `POST sidecars/:name/exec` | `sidecars.spawn` | `{ exitCode, stdout, stderr, truncated, timedOut }` |
| `GET sidecars/:name/logs?tail&since&timestamps=1` | `sidecars.spawn` | `{ stdout, stderr }` |
| `GET sidecars/:name/mounts` | `sidecars.spawn` | `{ capable, mounts }` (own + inherited) |
| `POST sidecars/:name/mounts` | `sidecars.mounts` + `apps.mount` | `{ ok, mount }` — body `{ targetAppId, mode?, data? }` |
| `DELETE sidecars/:name/mounts/:mountId` | `sidecars.mounts` + `apps.mount` | `{ ok }` — 409 for an inherited mount |

Without a token: `GET sidecars` (every sidecar, with usage; `?usage=0` skips
`docker stats`) and `GET mounts?includeSidecars=1`.

## From the CLI

```bash
aura get inst com.example.app sidecars        # ID, STATE, MANAGED, IMAGE
aura jump com.example.app --sidecar db        # shell inside it
aura exec inst com.example.app -c db -- pg_isready
aura logs inst com.example.app -c db --tail 50
aura describe sc db -i com.example.app
aura mount ls --instance com.example.app      # incl. sidecar mounts
```

## App-managed sidecars

The original path, for apps that need full control: the SDK runs docker
itself. It requires `sandbox: "container"` and `"docker"` in `tools[]` — the
OS binds the host docker socket only then, which makes the app host root.

```js
import { readFileSync } from 'node:fs';
import { createSidecars } from '@aura/app-sdk/sidecars';

const manifest = JSON.parse(readFileSync('./app.manifest.json', 'utf8'));
const host = createSidecars({
  appId:      process.env.APP_ID,
  instanceId: process.env.APP_INSTANCE_ID,
  appPort:    Number(process.env.APP_PORT),
  services:   manifest.services,          // mode defaults to 'docker'
});
await host.ensureAll();                   // idempotent
// host.teardownAll() from onDestroy
```

`mode: 'auto'` picks `'os'` when the app has no docker socket but a token,
else `'docker'`.

**Things that differ from the OS path:**

- **`ensure()` short-circuits on a running container.** Editing `services[]`
  does nothing until the container is gone: `docker rm -f aura-<instanceId>--<service>`.
  (The OS path compares a spec hash and recreates by itself.)
- **`inheritMounts` shares the app's mount root.** A sidecar started *after*
  the app already has mounts sees those directories **empty** — docker's
  volume mount is non-recursive, so only binds made while the sidecar runs
  propagate in. OS sidecars don't have this problem: their mounts are applied
  after start.
- **`volumes[]` can use `volume` / `subpath`** to park state anywhere on the
  shared volume, and `onSeed` can seed it with a helper container.
- **`inheritIdentity` forwards the app's own token**, so the sidecar acts as
  the app.
- The SDK reads the **raw** manifest (`JSON.parse(readFileSync(...))`); keep
  it that way, the SDK accepts fields the OS has no use for (`publish` with
  docker semantics, `volume`/`subpath`).

### Worked example — Hermes

A foreign agent image with every flag on, including the docker socket
(it spawns its own sandboxes):

```jsonc
"tools": ["bash", "node", "docker", "*"],
"permissions": ["storage.read", "storage.write", "network.internet", "apps.mount"],
"services": [{
  "name": "runtime",
  "image": "nousresearch/hermes-agent:latest",
  "command": ["gateway", "run"],
  "port": 9119,
  "proxyDashboard": true,
  "env": { "HERMES_DASHBOARD": "1", "HERMES_DASHBOARD_PORT": "9119" },
  "envInherit": ["OPENROUTER_API_KEY", "ANTHROPIC_API_KEY", "OPENAI_API_KEY"],
  "inheritIdentity": true,
  "inheritPermissions": true,
  "inheritTools": true,
  "inheritMounts": true,
  "inheritDockerSocket": true,
  "volumes": [{ "name": "data", "target": "/opt/data",
                "volume": "aura_aura-app-data", "subpath": "aura/runtime/com.aura.hermes/hermes-home" }],
  "dns": ["8.8.8.8", "1.1.1.1"]
}]
```

For contrast, a database template sets **no** inheritance flags — it needs
neither your identity, your tools, nor your mounts. That's the right default.

## All `services[]` fields

| Field | Notes |
|---|---|
| `name`, `image`, `command` | Template id (kebab-case), image, CMD. Many images exit without an explicit subcommand. |
| `port`, `proxyDashboard` | Port to reach (and `wait.port`), and which service the SDK's `listen()` proxies as the app window. |
| `env`, `envInherit` | See [Inheritance](#inheritance). |
| `volumes[]` | `{ name, target, shared? }` (+ `volume`, `subpath` on the SDK path). |
| `dns`, `restart` | Sidecars get no DNS by default — set it if the runtime reaches the internet. Restart default `unless-stopped`. |
| `user`, `workdir`, `limits` | `--user`, `--workdir`, `{ memory: "512m", cpus: 1.5 }`. |
| `seed` | `{ command: [...] }` — one-shot init (OS path). |
| `inheritIdentity`, `inheritPermissions`, `inheritTools`, `inheritMounts`, `inheritDockerSocket` | See [Inheritance](#inheritance). |
| `capabilities`, `devices`, `privileged`, `publish` | Kernel/host grants. OS path: need `sidecars.privileged`. Prefer the narrow ones over `privileged`. |
| `prePull`, `readiness` | Declared, not implemented yet. |
